# 월간 운영 보고서 생성기 (Claude Code 플러그인)

운영 로그 월간 추출 JSON **경로 하나로** 시사점 중심의 월간 운영 보고서(Chart.js 슬라이드 HTML)를 만듭니다. 여러 팀이 각자의 데이터·분류체계 성숙도로 함께 쓰도록 만들었습니다.

## 빠른 시작

**1. 설치** — Claude Code에서 한 번만.

```
/plugin marketplace add mjun94/ops-logger-report
/plugin install ops-report@jun-plugins
```

**2. 실행** — 월간 추출 JSON 경로를 넘깁니다.

```
/ops-report:monthly ./data/requests_202607.json
```

**3. 확인** — 집계 오버뷰(대상월·총건수·채널·유형)가 나오면 공휴일·담당자 부재만 답해 주세요. 승인하면 `report/<연도>/` 아래에 HTML 보고서가 생성됩니다.

프로필이 없는 첫 실행이면 그 자리에서 만들고 이어서 진행하므로, 처음 쓰는 팀도 이 세 단계가 전부입니다.

> 로컬 테스트: 저장소를 클론한 뒤 `claude --plugin-dir <클론 경로>`

## 사용법

**경로를 잊었으면 그냥 실행하세요.**

```
/ops-report:monthly
```

`data/` 아래에서 후보 파일을 찾아 대상월과 함께 보여줍니다. 이미 보고서를 만든 달은 표시되므로 중복 작업을 피할 수 있습니다.

**보고서는 승인 후에 만들어집니다.** 집계가 끝나면 대상월·총건수·채널·유형·데이터 한계·저장 위치를 먼저 보여주고, 그 자리에서 공휴일·담당자 부재를 함께 묻습니다. 답을 주면 시사점 작성이 시작됩니다. 파일이나 달이 잘못됐으면 이 지점에서 멈출 수 있습니다.

**프로필만 따로 만들려면** — `monthly`가 알아서 처리하므로 보통 필요 없습니다.

```
/ops-report:setup ./data/requests_202607.json
```

## 자동으로 처리되는 것

| 항목 | 동작 |
|---|---|
| 경로 없이 실행 | `data/` 아래 후보 파일을 찾아 대상월과 함께 제시 — 이미 보고서가 있는 달은 표시 |
| 프로필이 없을 때 | 별도 셋업 없이 그 자리에서 만들고 이어서 진행 |
| 프로필·베이스라인 찾기 | 데이터 폴더에서 위로 거슬러 올라가며 자동 탐색 (폴더 깊이 무관) |
| 출력 경로 | `report/<대상연도>/<제목> N월 보고서(YY.MM.DD).html` 자동 생성 (폴더까지) |
| 전월 비교 | 베이스라인이 있으면 자동, 없으면 첫 보고서로 비교 없이 생성 |
| 베이스라인 갱신 | 보고서 생성 후 당월 수치·다음 달 확인 포인트 자동 기록 |
| 데이터 한계 | 처리시간·요청자명이 없으면 관련 지표를 빼고 각주를 자동 삽입 |
| 분류체계 | 팀 확정 문서(`taxonomy.md`)가 있으면 그 기준으로 배정, 없으면 원문에서 도출해 제안 |
| 05장 분석 축 | 여러 조직을 상대하면 조직별, **한 회사만 담당하면 요청자 부서별**로 전환 |
| 문체 | 보고서 전체를 명사형 종결(보고서체)로. `~습니다`체가 남으면 빌드가 경고 |

사람이 매달 해야 하는 일은 **공휴일·담당자 부재·특이 이벤트를 확인해 주는 것**뿐입니다. 데이터에 없는 정보라 물어볼 수밖에 없습니다.

## 설계 원칙

| 역할 | 담당 | 이유 |
|---|---|---|
| 숫자 집계 | `aggregate.py` | 같은 입력 → 같은 결과. LLM이 세지 않는다 |
| 표·차트 레이아웃 | `compose.py` + `renderer.html` | 매달 1000줄 HTML을 손으로 고치지 않는다 |
| **시사점 해석** | `insight-analyst` 에이전트 | 이 보고서의 실제 가치 |
| 시사점 검증 | `insight-critic` 에이전트 | 근거 없는 단정이 경영 보고로 나가지 않게 |
| 문체·분량 검사 | `build_report.py` | `~습니다`체와 장문 `lead`를 경고로 잡는다. 규칙만으로는 매달 드리프트한다 |
| 분류체계 도출·배정 | `taxonomy-builder` 에이전트 | 분류체계가 없는 팀도 첫 달부터 쓸 수 있게. 팀 문서가 있으면 도출 없이 배정만 |
| 정합성 검사 | `build_report.py` | 체크리스트 대신 빌드 실패로 막는다 |

팀 고유 정보(필드 매핑·분류체계·과거 수치·해석 관점)는 **플러그인 밖 팀 폴더**의 `profile.json` / `baselines.json`에 둡니다. 플러그인에는 어떤 팀의 운영 데이터도 들어 있지 않습니다 — `examples/` 아래 값은 형식 설명용 가상 데이터입니다.

## 팀 폴더 구조

**데이터는 `data/` 아래 원하는 대로 두면 됩니다.** 플러그인이 요구하는 건 경로 하나뿐이고, 정리 방식은 강제하지 않습니다. 자동으로 정해지는 건 **보고서가 쌓이는 자리**뿐입니다.

```
우리팀-운영보고/                              ← 팀 루트 (profile.json 위치 = 모든 경로의 기준점)
├── profile.json                              setup이 생성
├── baselines.json                            매월 자동 누적
├── taxonomy.md                               팀 확정 분류체계 문서 (선택 — 있으면 배정 기준)
│
├── data/                                     입력 — 정리 방식은 자유
│   ├── 2026/requests_202607.json                연도별로 나눠도 되고
│   ├── requests_202512.json                     평면으로 둬도 되고
│   └── 아카이브/2025/requests_202503.json         더 깊어도 됩니다
│
├── report/                                   산출물 — 플러그인이 연도별로 만듭니다
│   ├── 2026/
│   │   ├── Ops Logger 6월 보고서(26.07.02).html
│   │   └── Ops Logger 7월 보고서(26.08.03).html
│   └── 2027/
│       └── Ops Logger 1월 보고서(27.02.04).html
│
└── report-work/                              중간 산출물 (매 실행 덮어씀)
    ├── stats.json
    ├── narrative.json
    └── report.json
```

| 위치 | 규칙 |
|---|---|
| `data/` | **자유.** 어디에 두든 프로필을 거슬러 올라가 찾습니다. 폴더를 만들거나 파일을 옮기지 않습니다 |
| `report/<연도>/` | 유일하게 플러그인이 정하는 자리. 연도는 **데이터의 대상월** 기준이라 26년 12월분을 27년 1월에 만들어도 `report/2026/`에 들어갑니다 |
| `report-work/` | 매달 같은 파일을 덮어쓰는 임시 작업물이라 연도로 나누지 않습니다 |
| `profile.json`·`baselines.json`·`taxonomy.md` | 팀 루트에 평면으로 둡니다. `baselines.json`은 누적 파일이라 쪼개면 연초에 전월 비교가 끊깁니다 |

팀 루트는 `profile.json`이 있는 폴더입니다. 스크립트가 데이터 경로에서 거슬러 올라가 찾으므로 **어느 위치에서 실행해도** 보고서가 같은 자리에 쌓입니다.

## 운영 분류체계 — 우리 팀은 뭘 하면 되나

팀 상황에 따라 할 일이 다릅니다. 어느 경우든 **첫 달부터 보고서가 나옵니다.**

| 우리 팀은… | 할 일 | 매달 일어나는 일 |
|---|---|---|
| 접수할 때 유형 코드를 입력한다 | 없음 | 데이터의 코드로 집계 (setup 때 코드→유형명 매핑만 확인) |
| 체계가 위키·문서로 있다 | 팀 루트에 `taxonomy.md`로 저장 — setup에서 붙여넣으면 변환해 줍니다 | 매달 이 문서의 유형으로 배정. 체계가 안 흔들려 월간 추이 비교가 안정됩니다 |
| 아직 없다 | 없음 — 그냥 실행 | 요청 원문에서 6~10개 유형을 도출해 보고서 04장에 제안 |

**제안이 마음에 들면 "확정"이라고 답하세요.** 그 체계가 `taxonomy.md`로 저장되고, 다음 달부터는 새로 도출하지 않고 같은 기준으로 배정됩니다. 고칠 유형이 있으면 수정 의견과 함께 확정하면 반영해서 저장합니다. 즉 **보고서를 만드는 과정이 분류체계를 확정하는 과정**이 됩니다.

`taxonomy.md`는 자유 형식입니다 — 팀 위키 내용을 그대로 붙여도 동작하고, 유형마다 정의·키워드·예시가 있을수록 배정이 정확해집니다. 권장 형식은 [taxonomy-template.md](./skills/monthly/references/taxonomy-template.md) 참조.

세부 규칙 두 가지: 코드가 일부만 있는 팀(partial)은 코드 있는 건이 항상 우선이고 나머지만 문서·도출 기준으로 배정됩니다. 코드가 90% 이상인 팀(coded)은 `taxonomy.md`가 있어도 집계에는 쓰지 않고 시사점 작성 시 유형 정의·용어 참고로만 씁니다 — 실제 처리 기록이 문서보다 우선입니다.

## 데이터 요구사항

- 형식: `{ "<추출 SQL>": [ {행}, … ] }` 또는 행 배열
- **요청일 기준으로 추출**할 것. 로깅일 기준이면 월말 요청이 익월로 넘어가 과소집계됩니다(자동 경고)
- 처리시간 분석을 원하면 `started_at`, 요청자 집중도 분석을 원하면 요청자명을 SELECT에 포함

## Ops Logger 당일 등록 플러그인 (`ops-logger`)

퇴근 전 한 번, 오늘 응대한 Google Chat·Gmail 문의를 골라 Ops Logger에 등록합니다. 수집·선택·분류는 Claude Code 안에서 하고 마지막 등록만 API로 보냅니다.

```
/plugin marketplace add mjun94/ops-logger-report
/plugin install ops-logger@jun-plugins
/ops-logger:setup            # 처음 한 번: 이메일 저장 + Google Chat 서버 등록 → /mcp 인증
/ops-logger:insert-today     # 매일: 오늘 문의 수집 → 선택 → 분류 → 등록
```

사용 매뉴얼: Confluence 그룹웨어팀 > Ops Logger 운영 가시화 > "Ops Logger 당일 등록 플러그인 사용 매뉴얼". 클라이언트 시크릿은 담당자에게 1:1로 받습니다. 레포에는 넣지 않습니다.
